# Tremor CRE workflow (`cre/`)

A Chainlink CRE workflow (TypeScript SDK `@chainlink/cre-sdk` 1.23.0, CRE CLI v1.39.0) that measures the
arbitrage loss (LVR) and volume of one block span of a Uniswap pool and writes them to `TremorReceiver`.
Spec: `docs/spec.md` §6.7 (report format), §7.5 (maths), §8 (workflow and call budget).

## Layout

| Path | What |
|---|---|
| `project.yaml` | CLI targets: `fork-settings` (Anvil at `http://127.0.0.1:8545`) and `production-settings` |
| `secrets.yaml`, `.env.example` | no secrets used; `.env` holds `CRE_ETH_PRIVATE_KEY` for `--broadcast` |
| `tremor-lvr/workflow.yaml` | workflow targets, config path `./config.fork.json` |
| `tremor-lvr/main.ts` | entry point (`Runner.newRunner({ configSchema })`) |
| `tremor-lvr/workflow.ts` | cron handler: reads, node-mode compute, consensus, report |
| `tremor-lvr/lvr.ts` | the §7.5 maths as pure bigint code, no imports; shared with `scripts/validate.ts` |
| `tremor-lvr/workflow.test.ts` | handler run on the SDK's test runtime with mocked EVM and HTTP |
| `tremor-lvr/config.fork.json` | generated by `scripts/make-config.ts` from `contracts/deployments/fork.json` |
| `scripts/make-config.ts` | writes `config.fork.json` |
| `scripts/validate.ts` | checks `lvr.ts` against `data/markout_pool.py` on one real historical hour |
| `backfill.sh` | loops the simulation until the receiver reaches a target block |

## What one run does (spec §8)

| Step | Capability | Calls |
|---|---|---|
| `TremorReceiver.lastProcessedBlock()` → `from = last + 1` (or `startBlock` if 0) | `callContract` | 1 |
| Swap logs of `[from, min(from + 1199, maxToBlock)]` in ≤ 100-block chunks | `filterLogs` | ≤ 12 |
| `Multicall3.getCurrentBlockTimestamp()` at `from` and at `to` | `callContract` | 2 |
| Binance `UNIUSDT` and `ETHUSDT` 1m klines for `[tsFrom − 60 s, tsTo + 60 s]` | HTTP GET (node mode) | 2 |
| Per-swap time interpolated by block; price interpolated in the minute; §7.5 sums | node mode | – |
| `{fromBlock, toBlock, toTimestamp, lvrUsdWad, volumeUsdWad, nSwaps}`, every field `identical` | consensus | 1 |
| `abi.encode(uint64,uint64,uint64,int256,uint256,uint32)` → `runtime.report` → `writeReport` | write | 1 |

That is at most 15 EVM reads and 2 HTTP calls. A 1,200-block span (about 4 h) needs about 242 kline rows per
symbol, about 40 KB per response (limit 250 KB). Only six integers go to consensus (limit 25 KB). A span with no
swaps skips the HTTP calls and reports zeros so the receiver still advances. If `from > maxToBlock` the run logs
`caught-up` and writes nothing.

**Sources** (`source.kind` in the config):
- `v3` (demo default): UNI/WETH 0.3% `0x1d42064Fc4Beb5F8aAF85F4617AE8b3b5B8Bd801`, topic0
  `0xc42079f9…ca67`, amounts already pool-perspective, fee 3,000 pips.
- `v4`: PoolManager `0x000000000004444c5dc75cB358380D2e3dE08A90`, topic0
  `0x40e9cecb9f5f1f1c5b9c97dec2917b7ee92e57ba5563708daca94dd84ad7112f`
  (`Swap(bytes32,address,int128,int128,uint160,uint128,int24,uint24)`), topic1 = `poolId`. Amounts are negated
  (swapper → pool perspective); the fee is the event's own `fee` field (pips).

**Maths** (`lvr.ts`, equal to `data/markout_pool.py`): price at second `t` = `open + (close − open)·clamp((t −
candleOpen)/60, 0, 1)` of the last candle opened at or before `t`; `value = a0·P_UNI + a1·P_ETH`;
`fee = feeRate · (a0 > 0 ? value0 : value1)`; `lvr = fee − value`; `volume = |a1|·P_ETH` (spec §7.5). All in
WAD USD bigints, truncating division, so every node gets the same integers.

## Setup

```bash
# CLI (official installer, docs.chain.link/cre/getting-started/cli-installation/macos-linux)
curl -sSL https://app.chain.link/cre/install.sh | bash      # installs to ~/.cre/bin
cd cre/tremor-lvr && bun install && cd ../scripts && bun install && cd ..
```

## Config from the deployment

`contracts/deployments/fork.json` is written by the contracts deployment. Generate the workflow config from it
(from `cre/`):

```bash
bun run scripts/make-config.ts --start-block 23515012          # v3 source (default)
bun run scripts/make-config.ts --source v4 --start-block <n>    # Tremor's v4 pool instead
```

It takes `receiver`, `multicall3`, `refV3Pool` (v3) or `poolManager` + `poolId` (v4) and `forkBlock` from
`fork.json`, checks `chainId == 1` and that the pool's tokens are UNI/WETH, and writes
`tremor-lvr/config.fork.json`. Defaults: `maxToBlock = forkBlock`, `startBlock = forkBlock`,
`blocksPerRun = 1200`, `gasLimit = 5,000,000`.

- `startBlock` is used only while `receiver.lastProcessedBlock() == 0`. If the owner has called
  `receiver.setStartBlock(n)`, the first span starts at `n + 1` and `startBlock` is ignored.
- The demo week 2025-10-06 is blocks **23,515,012 – 23,565,080** (first blocks of 2025-10-06, -13 and -20 UTC:
  23,515,012, 23,565,081, 23,615,117; found by timestamp binary search on `rpc.mevblocker.io`).
- The receiver in the current `fork.json` is `0xb10D1449D9506472C1DD8099e52dcb4bACfef927` (forkBlock
  26,351,695). Re-run `make-config.ts` whenever `fork.json` changes.

## Simulate against the Anvil fork

Requirements:
1. **`cre login`**. CLI v1.39.0 refuses `cre workflow simulate` without credentials ("Authentication
   required: not logged in and no CRE_API_KEY set"); `cre workflow build` does not need them.
2. **Anvil must fork from an archive RPC.** The workflow reads logs and calls Multicall3 at blocks long before
   the fork block; Anvil forwards those to its `--fork-url`. Use e.g.
   `anvil --fork-url https://rpc.mevblocker.io --chain-id 1` (that RPC served the historical `eth_getLogs` and
   `eth_call` in `validate.ts`). A non-archive upstream fails these reads.
3. `cre/.env` containing `CRE_ETH_PRIVATE_KEY=<one of Anvil's funded test keys>` (see `.env.example`). It signs the
   transaction to the forwarder.

The mainnet MockKeystoneForwarder `0xa3d1ad4ac559a6575a114998affb2fb2ec97a7d9` is built into the CLI for
`ethereum-mainnet` and already has code in forked state. `TremorReceiver` must be deployed with that forwarder and
no expected workflow id/owner/name (spec §6.7). `project.yaml` points `ethereum-mainnet` at
`http://127.0.0.1:8545` under the `fork-settings` target.

One run (from `cre/`):

```bash
cre workflow simulate ./tremor-lvr --target fork-settings --broadcast --non-interactive --trigger-index 0
```

Check the receiver advanced and the event fired:

```bash
cast call 0xb10D1449D9506472C1DD8099e52dcb4bACfef927 "lastProcessedBlock()(uint64)" --rpc-url http://127.0.0.1:8545
```

## Backfill

```bash
./backfill.sh <target-block> [max-runs]      # e.g. ./backfill.sh 23565081
```

It reads `lastProcessedBlock()` from the receiver in `config.fork.json` (override with `RECEIVER=`, RPC with
`RPC_URL=`), runs the simulate command above until `lastProcessedBlock >= target`, and stops if a run does not
advance it or after `max-runs` (default 200). The target must be ≤ `maxToBlock`.

For the 2025-10-06 week from a fresh receiver: `make-config.ts --start-block 23515012`, then
`./backfill.sh 23565081`. That is 42 runs; the run that crosses into the 2025-10-13 epoch (span
`[23564212, 23565411]`) closes the week and sets the premium. Its blocks of the old week are attributed to the new
epoch (the spec §6.7 approximation, here about 869 blocks ≈ 2.9 h).

## Checks

```bash
cd tremor-lvr && bunx tsc --noEmit && bun test && cd ..   # typecheck + handler tests on the SDK test runtime
cd scripts && bunx tsc --noEmit && cd ..                   # typecheck scripts
bun run scripts/validate.ts [--hour 2025-10-10T21:00:00Z]  # lvr.ts vs data/markout_pool.py, real data
cre workflow build ./tremor-lvr                            # compile to WASM (no login needed)
```

`validate.ts` finds the hour's blocks, fetches the v3 pool's logs in 100-block chunks and the span timestamps via
Multicall3 from `rpc.mevblocker.io`, fetches klines with the workflow's URL, computes with `lvr.ts`, and runs the
unmodified `data/markout_pool.py` on the same swaps and candles: (A) with the workflow's interpolated timestamps
and (B) with real block timestamps. It exits non-zero if any TS/Python difference exceeds the tolerance.

## Known limits

- **Volume definition.** `markout_pool.py` reports `volume_usd = Σ|a0|·P_UNI`; spec §7.5 (and this workflow)
  uses `Σ|a1|·P_ETH`. They differ when the pool trades away from Binance: in the 2025-10-10 21:00 UTC hour,
  $3,399,280 vs $4,026,722. `validate.ts` checks both.
- **Timestamp interpolation.** Per-swap time is linear in block number between the span's end timestamps, off by
  up to 11 s in the hours checked (missed slots). In the 2025-10-10 21:00 crash hour that moved LVR by $5,370 of
  $152,563 (3.5%); in a calm hour it was negligible.
- **Head cap.** The span is capped by `maxToBlock` from the config, not by the chain head (reading the head would
  be a 16th EVM read). On the fork, `maxToBlock = forkBlock`. A live deployment needs a different cap.
- Simulation was not run end to end here (needs `cre login`). Build, typecheck, handler tests and the validation
  ran.
